## What was the main change in strategy this week compared to last week? What prompted it?

Week 1's strategy was pure random search — a uniform draw from the domain,
constrained only by bounds and duplicate-avoidance, with no model behind it
at all. Week 2 introduced the **first real modelling step**: fitting a
Gaussian Process surrogate (compared across RBF and Matérn kernels) to each
function's data and visualising its posterior mean and uncertainty. This is
a real strategic shift — from "no informed basis for a query" to "a
quantified belief about the function's shape and where it's uncertain" —
but it's a preparatory shift, not yet an executed one: no acquisition
function was applied, so no query decision was actually made differently
this week. What prompted it was simply that this is the natural next step
once a second real observation exists per function; fitting a surrogate on
literally two points (for most functions, the original starter set plus one
appended observation) is not yet informative in any strong sense, but
establishing the pipeline — kernel choice, standardisation, noise
modelling, convergence checking — now means it's ready to actually drive a
query once there's more reason to trust it. It was not prompted by
acquisition-function behaviour, since none has been used yet.

## Exploration or exploitation this week? Why? What trade-offs?

Neither was chosen this week, in the sense of an actual query decision — no
query was submitted. But the surrogate work did surface exactly the
information that decision would need: the posterior standard deviation maps
(2D contour for Function_01/02, 1D slices elsewhere) show where the model is
still highly uncertain (almost everywhere, given only 11–41 points spread

high. If a query had been chosen this week, the honest answer is it would
have leaned toward **exploration**, because with this little data any
"promising region" the GP identifies is built on very weak evidence —
exploiting it would risk chasing an artifact of small-sample noise rather
than real structure. The trade-off being weighed for when acquisition-based
querying does start: UCB's `kappa` or EI's `xi` parameter controls exactly
this balance, and given how sparse coverage is for the higher-dimensional
functions (Function_07, Function_08), those functions will likely need a
higher exploration weighting than the 2D functions, where a single new
point covers proportionally much more of the space.

## If a linear or logistic regression were fit to current data, which assumptions would likely be violated?

Taking **Function_05** as the clearest example: a linear model assumes a
roughly constant marginal effect of each input across the domain (global
linearity), homoscedastic and independent noise, and enough observations
relative to the number of features to estimate coefficients reliably.
Function_05 violates several of these visibly. Its output ranges from
~0.11 to beyond 1000 across the observed data — a swing of four orders of
magnitude that is very unlikely to be explained by a linear combination of
four bounded-[0,1) inputs; the GP fit's own length-scales (short on some
dimensions, pinned at the upper bound on others) point to non-uniform,
direction-dependent curvature rather than a flat linear surface. There's
also now direct evidence of noise: a near-duplicate query pair with a ~0.006
output difference at essentially the same input, which a linear model's
usual homoscedastic-Gaussian-noise assumption doesn't have any special
mechanism to accommodate once outputs span such a wide range. Sample size
is also a real constraint: 21 observations against 4 features (plus an
intercept) is workable for ordinary least squares narrowly, but leaves very
little room to check whether the fit generalises, especially once one
appended point is a near-duplicate of an existing one and contributes
little new information.

**Function_08** is a useful second case for the sample-size point
specifically: 41 observations against 8 features is a much tighter ratio,
and the GP fit for this function had one dimension's length-scale pinned at
its upper search bound — suggestive of little detectable structure along
that axis with this little data, which a linear model would either
similarly fail to resolve or could spuriously "explain" with an unstable
coefficient given the limited degrees of freedom.

## Are there regions that look roughly linear, or where a decision boundary might form? How might logistic regression perform there?

The GP fits already surfaced a concrete, evidence-based answer to the first
half of this question, rather than requiring a fresh linear fit to find
out: several individual dimensions had their fitted length-scale converge
to the search-space upper bound (Function_01's 2nd dimension; Function_03's
1st and 2nd dimensions; Function_07's 2nd and 3rd dimensions; Function_08's
8th dimension). A length-scale pinned at the upper bound means the GP found
no useful correlation structure across that dimension within the allowed
range — effectively, "the output doesn't depend much on this input," which
is the closest thing to "locally linear/flat" this analysis has evidence
for. In those specific directions, a simple linear term might actually
capture the (near-absence of) effect reasonably well.

For a binary/threshold scenario (e.g. "is the output above the median
observed so far"), logistic regression's performance would likely depend
heavily on which function and which threshold. Functions with a wide,
skewed output range and a small number of very large values (Function_05
again, and to a lesser extent Function_08) are exactly the case where a
simple linear decision boundary is least likely to separate "high" from
"low" outputs cleanly, since the extreme values are driven by localized,
nonlinear structure the GP's own length-scales already show is not
uniform across the domain. Functions with narrower, more evenly spread
output ranges and more flat/linear dimensions (e.g. Function_02, which the
GP fit with a comparatively short, well-behaved length-scale set) would be
more plausible candidates for a logistic classifier to do reasonably well,
though this project has not actually fit or tested one, so this remains an
informed expectation rather than a verified result.

## Was considering individual feature effects useful before deciding on a query point?

Yes, in spirit, even though no new query was actually decided this week.
The 1D slice plots built into each Week 2 notebook — varying one input
dimension at a time while holding the rest at the current best-observed
point, and showing the posterior mean with an uncertainty band — are
functionally similar to what a linear or logistic model's individual
coefficients would show: a per-feature view of how the model believes the
output responds along each axis in isolation. This was useful for spotting,
without needing a separate linear model, which dimensions the current data
says the most about (steep, well-constrained slices) versus which remain
essentially unconstrained (flat slices, often coinciding with the
length-scale-pinned-at-bound dimensions noted above). That per-feature
diagnostic is exactly the kind of interpretability check that should happen
*before* trusting an acquisition function's recommendation once querying
resumes — if a dimension's slice is flat purely because there isn't enough
data to say anything about it yet, that's different from it being flat
because the function truly doesn't depend on it, and conflating the two
would be a mistake going into the next round.
